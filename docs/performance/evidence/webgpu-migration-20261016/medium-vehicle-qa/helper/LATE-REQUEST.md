Separate reachable case: Game.setQuality has no ready gate. It writes AdaptiveQualityController.setMode, while applyAdaptiveQuality intentionally defers effective rendering during preparingRenderQuality. UI has game.current assigned during await g.start and settings onChange calls setQuality. The new actual test extracts the real setQuality/applyAdaptiveQuality methods, uses the real AdaptiveQualityController, starts all qualities requested Medium and calls setQuality(High) during current-off in the final temporary Medium pass. Proposed smallest correction pending coordinator scope authorisation: add optional requestedQuality getter to copied render-quality-preparation.ts and supply it from actual Game adaptive state. After successful final-pass result and normal elapsed/retirement checks, compare latest valid requested quality with the quality just prepared. If different, append that quality as another final pass using existing apply/prepare/restore pipeline. No restart of started, paused accounting or original total90s deadline; per-pass budget stays min(30s,remaining total). Further genuine changes may need another tail pass but share that same total deadline. Failure/disposal stops normally. All original three qualities always run, stable case remains48stages; late requests add16stages/pass and can time out rather than falsely report ready.

Rejected alternatives: inactive map resizing only would create fresh unprepared pass/RTT and not prove receiver variants; generator/effect caches add unapproved resource lifetime and identity risks; replacing entire orchestration or globally restarting stages is broader than reusing bounded existing quality pass. Merely restoring earlier cannot prevent a still-later request during accepted draws. This correction is not yet implemented in this document's checkpoint and must not be advertised as complete until its actual map test and total-deadline tests pass.
