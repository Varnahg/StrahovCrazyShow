# Vehicle quality preparation decision

Evidence: current actual capture3320 contains entry-time VehicleLighting.updateBeam/shadow target/pass creation and light resync stack frames. This is presence, not measured CPU share; the 6/9 new programs are not individually all attributed to this omission. Exact base is current clean067 with accepted SDWf8 and garment068, not older8fb. No dependency patch is proposed.

Current chain: Game.prepareLighting wraps WebGPU in prepareRenderQualities, fixed three passes with requested initial quality last, per-pass30s and total90s visible deadlines. Requested adaptive changes are retained while temporary render quality suppresses normal application, final restore applies latest requested quality/scaling before full readiness draws. WebGL bypasses the wrapper. prepareLightingVariants currently enables vehicle stages only for Low, creates AuthoredLightPreparation only there and retains concrete car/parked leases. apply first runs actual world/environment, then clamps mapped POINT count to quality1/2 and four minus actual enabled nonStreet sources, then selects authored layout/light-membership representatives. Progress plus two complete ready draws, engine effect and pipeline readiness, revision restarts and cleanup remain required.

Actual VehicleLighting: active car spotlight range32/angle0.8, no shadow pass at Low; Medium uses256, High512, PCF low quality unchanged. Off retains configured shadow state/resources without taking a light slot. Player flashlight is a distinct existing beam. applyArtLighting reserves ambient, celestial if enabled, car and actual interior/torch slots; with ambient+car and no celestial/interior there are TWO actual POINT slots at Medium/High. With celestial on only ONE is available; other practical slots may reduce to zero. Thus merely enabling existing0/1 stages at every quality is incomplete. prepareLightVariants has fixed stage array and restarts only current stage when quality/profile/assets change.

Options compared:

1. Enable old0/1 at all qualities: minimal text but misses real2POINT/shadow variants, rejected.
2. Initial-quality-derived0/1 or0/1/2: skips one Low duplicate but stage set is fixed. A live quality revision can increase capacity while a pass waits; correctness then requires rebuilding/restarting orchestration and checking coverage. More mutable state, no need to save three Low progress/acceptance draws. Rejected.
3. Stable0/1/2 at every WebGPU pass: selected. The existing runtime clamp resolves actual budget/quality each apply. Low vehicle2 repeats its clamped1 membership (same visual shader state), explicitly accepted one-stage startup overhead. Existing revisions reapply current stage, all three requested counts stay available. 16stages/pass,48total instead of prior Low15+Medium13+High13=41. No shadow suppression, timeout increases, new cache/profiler or new runtime resource.
4. Restart whole quality sequence on each requested quality revision: redundant with already-fixed three quality passes and latest restore, greater startup/reentrancy risk; no necessity for this missing fixed matrix.

Implementation scope is two copied runtime files: rename internal option to includeVehicleVariants, extend typed vehicle stage to0|1|2, enable for all native WebGPU qualities, reuse existing authored representative selection and ownership/cleanup. Other Game behavior, camera/actor/physics, actual shader/material/light values and timeouts remain untouched. WebGL retains original9 stages and no vehicle lease.

Tests must establish actual256/512shadow map and shadow-enabled receiver behavior, nonvacuous2POINT with actual key below horizon, zero/one/two mapped counts constrained by enabled source budget, Low clamp redundancy, requested-quality/revision/restore and dead/replaced roots. CPU draws/NullEngine prove wiring/lifecycle and actual GLSL effect identity, not native WGSL/pipeline or FPS acceptance. Actual Edge remains required.
