# Rozhodnutí před kandidátní implementací

Aktualizace3.11.2026: původní experiment není přijatý. [Forenzní rozbor všech selhání](startup-forensics.md) odděluje skutečnou validační chybu80/96 od zbývajícího timeoutu candidate2 a určuje další kontrolní srovnání. Nejnovější běh má13,117s renderovacích volání a4,515s kontrol objektů; přímá shaderová tvorba už v tomto jednom pokusu nebyla dominantní. To není důkaz příčinného zisku ani úspěšného startu.

Výchozí produkční build má source/test SHA `a03e0c635074c656ad73259b1626d3dafbe9e79ebd0a6e843f22c01fb684f904`, commit `fdc7b919`. [Naměřené souhrny s raw SHA](baseline.json) zachovávají i neúspěchy. Rozlišené CPU/GPU/síťové a paměťové pojmy se nezaměňují.

První problém prostředí byl skutečně neaktivní browser tab. Edge management vracel active=false. Podporovaný přesun téže karty do samostatného focused normálního okna změnil active=true; v novém startu stejného kódu presentation probe přešla z přibližně1Hz na59,9–60,2Hz. Neaktivní série není FPS důkaz. DOM visible/focused samo nestačilo. Původní uživatelská8080 karta měla0canvas a nebyla změněna.

V normálním foreground startu se Low připravilo za24,314s, High selhalo při day-1-on: jeden render20,8265s, z toho35 pomalých createShaderModule volání18,1085s. Jde o nativní synchronní volání na main thread, nikoli GPU execution time. Enclosing shaderPreparation měří převážně stejnou práci a nesčítá se s module časy. Přesná příčina dlouhých nativních callů uvnitř driveru/prohlížeče není potvrzená. V kritickém systémovém intervalu bylo10 celokaretních vzorků s GPU5% a VRAM3779–3805/6144MiB, bez thermalflagů; to nedokazuje memorypressure ani absenci krátkých špiček.

Samostatný instrumentovaný pokus potvrzuje drahé denní varianty, ale shader inventory samo zabralo4,493s CPU. Rozšířený profiler se nesmí porovnávat s běžnou hrou jako identická režie. Ze1400 module calls má884 známých textů8 přesných opakování;516 nezachycených callů není důkaz unikátnosti. Proto zatím není dost podkladů pro cache jako hlavní zásah. Odstranění defines navíc vyžaduje sémantický důkaz. Menší cap async pipeline práce by neomezil dřívější burst shader modules; cap64 je až za jejich vytvořením.

Zvolený experiment: kooperativně dávkovat spuštění přípravy čerstvých shader contexts jen během zakrytého quality/light/startup scope. Časový rozpočet4ms a počet4jobs platí pro zahájení další práce; jeden nativní call nelze preemptovat. Zachovat všechny varianty, kontrolní renderování, health a submission brány a30/90s timeouty. Queue přidává dočasné reference na již existující vstupy, nikoli trvalou shader cache. Pending/retirement/disposal musí být kryté testy. Celkový čas může zhoršit menší paralelismus, proto přijetí závisí na novém skutečném měření; teď jde o kandidáta.

Primární implementační zdroje jsou instalované Babylon9.30 `webgpuEngine.pure.js`, `effect.functions.js`, `effect.pure.js`, `webgpuPipelineContext.js` a `buffer.nonFloatVertexBuffers.js`. Native async entry point čeká na callback, zatímco návratová Promise je volajícím ignorovaná. Context se stages má synchronní rebuild kontrakt; zůstává v passthrough. WebGPU release nemusí zavolat context.dispose, proto se sleduje i _deletePipelineContext. Finální úklid nesmí po nahlášené chybě pustit ready.

[WebGPU CRD15.9.2026 — shader module creation](https://www.w3.org/TR/2026/CRD-webgpu-20260915/#dom-gpudevice-createshadermodule) rozlišuje content/device timeline; návrat handle není dokončení všech validačních a kompilačních prací. [Asynchronní pipeline creation](https://www.w3.org/TR/2026/CRD-webgpu-20260915/#async-pipeline-creation) poskytuje Promise dokončené pipeline. Proto zůstávají původní skutečné validation/pipeline/submission kontroly; naše fronta je rozdělení CPU přísunu, ne náhrada GPU synchronizace.
