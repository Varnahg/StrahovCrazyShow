## Returned review: moving peer during an asynchronous fence

Root/renderer review found a deterministic counterexample against the192-test checkpoint (Game16f053b1/render-startupbd15587d). Actual AST-selected Game stamp/coverage/gate methods plus the original RenderStartup, with terminal scalar IO, accept identical-pose packet objects in100ms/two draws. A remote x change of0.005 before every50ms fence settlement instead causes600 draws/submits and the original30s timeout, although coverage remains identical. This is a scheduling counterexample, not a real20Hz network or GPU latency/performance measurement. The192 proof is historical and insufficient for continuous movement.

Reason: the old after-fence readiness compares the validated submitted Scene with a newer network target that has not been rendered. Chasing every latest packet can require an infinitely quiet network window. Variants considered before the correction: (1) chase exact latest targets (rejected by the counterexample); (2) freeze remotes through the whole startup (unnecessarily stale and loses normal stage movement); (3) temporarily replace/restore targets or sample the timeline (unnecessary stream/interpolation ownership and lifecycle risk); (4) predict the next LOD from targets (duplicates actual LOD hysteresis/material/scene-registration behavior); (5) **validate each finite rendered remote presentation snapshot** (selected explicitly by root).

Selected boundary: immediately before each real preload render, apply already-accepted remote targets with the original dt0 presenter. The rendered stamp then identifies the actual remote root position/orientation/LOD/visibility that was submitted, not the evolving target stream. During its asynchronous scope/fence, accepted targets continue to update unchanged. Post-fence readiness still requires exact self owner/epoch/anchor, live membership/profile and actual Scene/material/native/LOD/visibility coverage, and all original pipeline/effect/health/submission gates. A real Scene/LOD/profile change during the fence must retry. A future target crossing is coverage of the next render, not an already-submitted-frame claim. The next preload draw or original gameplay interpolation consumes newer targets normally. `preparationRemoteBoundary=submitted-frame` states this bounded technical boundary; no latest-at-release remote-pose guarantee is made. One frame's copied stamp is bounded by the known roster and adds no history/global cache/timeline mutation, no extra GPU/readiness calls and no new budget. Self authority and the original shared30s gate remain unchanged.
