## Plán integrace a ověření

1. **Problém.** Ultra 50 % a živá změna nastavení jsou zatím mimo main. Dokumentace obou větví mění stejný začátek ověřovacího přehledu.
2. **Doložený mechanismus.** Git merge-tree hlásí konflikt jen v docs/verification.md. Automatická kombinace UI potřebuje ověřit společný AI store, vstupní podmínky a fokus. PR mapuje Ultra na Low s explicitními příznaky a za běhu potvrzuje nastavení až po snímku. Zdroje jsou kontrakt, původní CI, lokální Babylon 9.30 a A/B z PR.
3. **Změna.** Třícestný merge přesného donoru. Sloučení zachová výsledky AI i grafiky, bez návratu historické výjimky pro D. Cherry-pick by rozdělil již provázané testy a evidenci a nepropojil historii PR. Ruční přepis by znovu otevřel vyřešené problémy s lifecycle. Samotný merge potřebuje cílenou kontrolu přechodů, cache a pozdních dokončení.
4. **Hlavní metrika.** Funkční přejímka potvrzené grafické transakce a stejné multiplayerové relace, odděleně pro WebGPU a WebGL2. Evidence zobrazení má obsahovat velikost canvasu a interního bufferu.
5. **Správnost.** Zachovat nové AI rozhraní, původní volby, readiness/health, rollback a uvolnění prostředků. Ověřit neměnný build, vstup do B6, jízdu, svítilnu za tmy a skutečný backend. Snapshot zahrne testy.
6. **Přijetí.** Cílené regrese, plná sada, build a izolovaná SDK integrace. Funkční browser ověření zdokumentovat po jednotlivých bodech. Původní 15,57% zlepšení mediánu je pod 20% prahem. Zůstávají původní frame a síťové meze pro jakýkoli závěr o plynulosti.

## Nález nezávislé kontroly

1. Problém. Výjimka při kreslení během přípravy světel mohla přejít do rollbacku.
2. Mechanismus. Tick přípravy zachytí výjimku před obálkou Babylon frame monitoru a vrátí failed/render. Bez nahlášení do RenderHealth zůstane canRestore zelené.
3. Změna. Nahlásit skutečnou chybu na hranici tohoto ručního draw a ponechat zpracování výjimky vlastníkovi přípravy.
4. Metrika. Jeden render fault, žádný rollback ani potvrzení nastavení, požadavek na restart.
5. Správnost. Zrušení a existující fatal nesmí přidat chybný či duplicitní fault. Obyčejný timeout zůstává obnovitelný.
6. Přijetí. Regrese s výjimkou během přípravy před submission musí selhat na původním kódu a projít po opravě.

Druhý nález má stejný přechod mezi přípravou a odesláním snímku. Pokud příprava vyčerpá čas dřív, než doběhne časovač, nulový limit vyvolá chybu API a zbytečný restart. Ověření před vstupem do brány udrží běžný timeout obnovitelný. Metrika a přijetí jsou jediný pokus o odeslání pro původní nastavení, validní RenderHealth a žádná změna uložených preferencí. Celkový limit ani pravidla odeslání se nemění. Obě nové regrese před opravou selhaly očekávanou asercí.
